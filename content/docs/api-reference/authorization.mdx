# API Authorization

Coolify authenticates API requests with Bearer tokens. After identifying the token and its user, Coolify checks the token's team, permissions, expiration, and instance access controls before running the endpoint.

## Before you make a request

Follow [API Tokens](/core/security/credentials/api-tokens) to:

- enable API access on a self-hosted instance
- create a token for the correct active team
- choose permissions and an expiration period
- copy the token into the caller's secret store

Use a separate token for each integration and team. Do not place tokens in source code, query strings, or deployment logs.

---

## Send a Bearer token

Include the complete token in the `Authorization` header of every protected request:

```sh
export COOLIFY_URL="https://coolify.shadowarcanist.com"
export COOLIFY_TOKEN="<api-token>"

curl --fail-with-body \
  --header "Authorization: Bearer $COOLIFY_TOKEN" \
  "$COOLIFY_URL/api/v1/teams/current"
```

The header format is:

```txt
Authorization: Bearer <api-token>
```

The token includes an ID, a `|` separator, and the secret value. Send the complete value exactly as Coolify displayed it when the token was created.

---

## Base URL

Versioned API endpoints use this base URL:

```txt
https://coolify.shadowarcanist.com/api/v1
```

The public health endpoint is also available at `/api/health`. Use the endpoint pages in the API Reference sidebar to find each HTTP method, path, request body, and response schema.

---

## Authorization checks

A protected request passes through these checks:

1. The token exists, has not expired, and authenticates a user.
2. The token is bound to a team that still includes that user.
3. On self-hosted Coolify, **API Access** is enabled and the caller matches **Allowed IPs for API Access** when an allowlist is set.
4. The token has the permission required by the endpoint, unless it has `root`.
5. A token using `write` or `root` still belongs to a team administrator or owner.

| Result | Typical meaning |
| :--- | :--- |
| `200`-`299` | Authentication and authorization passed; interpret the endpoint response for the operation result. |
| `401 Unauthenticated` | The token is missing, invalid, expired, revoked, or no longer belongs to a current team member. |
| `403 Forbidden` | API access or the caller's IP is blocked, the token lacks the endpoint permission, or the token owner lacks the role required for `write` or `root`. |
| `429 Too Many Requests` | The caller exceeded the API rate limit. |

A token's team is fixed at creation. If a resource belongs to another team, create a token while that team is active rather than trying to reuse the current token.

---

## Permissions and sensitive data

Most endpoints require `read`, `write`, or `deploy`. A `root` token bypasses those endpoint permission checks but remains team-bound. It does not bypass the self-hosted **API Access** switch or **Allowed IPs for API Access**.

The `read:sensitive` permission controls response redaction separately from endpoint access. A request may succeed with `read` while passwords, private keys, environment values, logs, or Compose content remain redacted. Add `read:sensitive` only when the integration needs those values.

Review the complete [token permissions table](/core/security/credentials/api-tokens#token-permissions) before issuing a credential.

---

## Self-hosted API access controls

On a self-hosted instance, **Settings > Configuration > Advanced** contains:

- **API Access**, which allows or blocks authenticated REST API requests
- **Allowed IPs for API Access**, which accepts comma-separated IP addresses and CIDR ranges

Leaving the allowlist empty or setting it to `0.0.0.0` allows requests from any source address. Add every required IPv4 or IPv6 address or network before saving a restrictive list.

Coolify Cloud does not use the self-hosted **API Access** switch for customer requests.

---

## Rate limits

The default API rate limit is 200 requests per minute. Self-hosted administrators can change it with the `API_RATE_LIMIT` environment variable.

When a request returns `429 Too Many Requests`, wait for the rate-limit window before retrying. Use backoff instead of sending the same request continuously.

The `/api/health` endpoint has a separate limit of 1,000 requests per minute.

## Troubleshooting

<Accordions type="multiple">
<Accordion title="A request returns 401 Unauthenticated">

Check the `Authorization` header for the `Bearer` prefix and complete token value. Then confirm that the token has not expired or been revoked and that its owner still belongs to the token's team.

If the user's password changed, create a replacement token because password changes revoke that user's issued tokens.

</Accordion>
<Accordion title="A request returns 403 Forbidden">

Check the response message and endpoint requirements.

- On self-hosted Coolify, confirm **API Access** and the source-IP allowlist.
- Add the required `read`, `write`, or `deploy` permission to a new token.
- For `write` or `root`, confirm that the token owner remains a team administrator or owner.

Token permissions cannot be changed after creation. Create a replacement and revoke the previous token.

</Accordion>
<Accordion title="A successful request omits or redacts sensitive values">

Use a token with `read:sensitive` in addition to the endpoint's required permission. A `read` token can access supported read endpoints without receiving sensitive fields.

</Accordion>
<Accordion title="A resource does not appear in the response">

Confirm that the resource belongs to the team bound to the token. Create a separate token while the other team is active when an integration needs access there.

</Accordion>
<Accordion title="A request returns 429 Too Many Requests">

Wait before retrying and reduce the request frequency. On a self-hosted instance, an administrator can review `API_RATE_LIMIT` when the workload requires a different sustained limit.

</Accordion>
</Accordions>
